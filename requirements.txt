NORTHSTAR POLICY COMPASS - APPLICATION REQUIREMENTS

1. PURPOSE AND SCOPE
Build a Retrieval-Augmented Generation (RAG) application that answers
questions using the supplied company policy corpus and exposes its evidence.
The supplied Northstar Cloud Services corpus is synthetic demonstration data.

2. FUNCTIONAL REQUIREMENTS
- Accept natural-language policy questions of 1 to 1,500 characters.
- Search all policies or restrict retrieval to one selected document.
- Ingest the 13 supplied Markdown documents, currently containing 61 sections.
- Preserve document titles, owners, versions, effective dates, source hashes,
  section identifiers, and original passage text where available.
- Show missing metadata as "Not specified" rather than inventing values.
- Retrieve up to six passages by fusing Qdrant semantic similarity and BM25
  keyword rankings with reciprocal rank fusion; label keyword-only fallback.
- Generate answers from retrieved evidence when an LLM API key is configured.
- Instruct the model to preserve qualifications, exceptions, approval roles,
  and deadlines, and to acknowledge missing evidence or conflicting policies.
- Cite factual claims with numbered references to retrieved passages.
- Validate citation numbers and fall back to source passages if validation fails.
- Provide clickable citations and a full policy document reader.
- Clearly label search-only results when LLM generation is not configured.
- Return a no-evidence response when retrieval finds no sufficient matches.
- Provide a searchable policy library, suggested questions, and copy controls.
- Save bookmarked answers and the latest 40 questions in browser localStorage.
- Allow users to remove bookmarks and clear recent questions.
- Provide responsive layouts and keyboard-accessible controls and dialogs.
- Show loading, empty, input-validation, network, and provider-error states.

3. SYSTEM AND RUNTIME REQUIREMENTS
- Node.js version 22.13.0 or later.
- npm and the dependency versions resolved by package-lock.json.
- A modern browser supporting JavaScript, fetch, and localStorage.
- Network access for dependency installation and live LLM requests.
- React frontend, Vinext application framework, and Cloudflare Worker backend.
- Sites private hosting for the deployed application.
- Semantic retrieval requires OpenAI text-embedding-3-small and Qdrant.
- Local Qdrant runs through Docker Compose with persistent named-volume storage.
- Hosted Qdrant must have an HTTPS endpoint reachable by the application.
- No Python runtime or pip packages are required. This file is documentation,
  not a pip manifest.

4. LLM CONFIGURATION
- Default generation provider: xAI Grok, LLM_PROVIDER=xai.
- Required for Grok answers: XAI_API_KEY, stored as a server-side secret.
- Optional XAI_MODEL defaults to grok-4.7.
- Obtain a separate xAI key from https://console.x.ai with model access and credits.
- Send evidence to https://api.x.ai/v1/responses with store=false, low reasoning,
  and a 120-second timeout. Validate citations before displaying generated text.
- Explicit OpenAI option: LLM_PROVIDER=openai, OPENAI_API_KEY, and optional
  OPENAI_MODEL (default gpt-4.1-mini), with a 45-second timeout.
- Never use a provider's key with another provider's endpoint.
- Configure hosted secrets in Sites runtime environment variables and redeploy.
- Local secrets belong in ignored .dev.vars; restart after editing.
- Do not put credentials in this file, source code, browser code, or Git.
- Without a generation key, display clearly labelled retrieved passages.
- Live Grok generation requires an xAI key and is not verified by mocked tests.

5. EMBEDDING AND VECTOR DATABASE REQUIREMENTS
- Use LangChain.js OpenAIEmbeddings for embedding requests and batching.
- Use LangChain QdrantVectorStore.addDocuments for ingestion and its
  asRetriever().invoke() interface for semantic retrieval.
- Use LangChain BM25Retriever for keyword scoring and EnsembleRetriever for
  reciprocal rank fusion; remove the previous custom scoring implementations.
- Use BaseRetriever wrappers only for policy validation, scope, and fallback.
- Use xAI Grok Responses API for generation by default; keep retrieval in LangChain.
- Store content and nested metadata using the LangChain Qdrant schema.
- Reindex into northstar_lc_ collections; preserve existing legacy collections.
- Do not auto-create collections from the question-answering request path.
- Model: OpenAI text-embedding-3-small, with 1,536-dimensional vectors.
- Vector database: Qdrant, using cosine similarity over persistent vectors.
- Local service: qdrant/qdrant:v1.18.0 via compose.yaml, localhost port 6333.
- Configure QDRANT_URL; configure QDRANT_API_KEY for authenticated deployments.
- Configure SEMANTIC_SCORE_THRESHOLD (0-1; default 0.35) and evaluate its quality.
- Index paragraphs in batches with npm run index:vectors after npm run ingest.
- Use the same embedding model and dimensions for ingestion and questions.
- Version collections by corpus content, model, and dimensions.
- Require a complete index with matching dimensions before serving vectors.
- Upsert stable point IDs and create a metadata.documentId keyword payload index.
- Filter by selected document and resolve returned IDs against canonical sources.
- Do not trust remote payloads to supply or replace policy text.
- Merge keyword and semantic ranks; deduplicate and renumber source citations.
- Label fallback when configuration, indexing, or a service is unavailable.
- Retain old collections; do not delete user data during reindexing.
- Keep database credentials server-side and use HTTPS outside localhost.
- Hosted deployment cannot connect to a laptop's localhost Qdrant service.

6. DATA AND INGESTION REQUIREMENTS
- Source policies reside in corpus/ as Markdown files.
- Use a single # document title and ## section headings.
- Generate data/corpus.json with node scripts/ingest.mjs.
- Split source text along section and paragraph boundaries.
- Do not ingest the companion PDF as duplicate evidence.
- Re-ingest, reindex vectors, test, build, and redeploy after policy changes.
- Update displayed corpus counts if document or section totals change.
- Preserve original policy content, including inconsistencies; do not silently
  rewrite policies during ingestion.

7. SECURITY AND PRIVACY REQUIREMENTS
- Keep the hosted application owner-private unless access is explicitly changed.
- Treat the development server as local-only; it has no standalone authentication.
- Keep model credentials server-side and scoped to request execution.
- Validate JSON requests, question length, document scope, and request origin.
- Return private/no-store API responses.
- Treat source documents and questions as untrusted prompt content.
- Render model output as text rather than executable HTML.
- Give the model no tools or authority to execute company actions.
- Explain that history and bookmarks are stored in the current browser.
- Send only the question and selected passages for each independent question;
  conversation history is not sent to the model.

8. INSTALLATION AND EXECUTION
Run these commands from the policy-assistant project directory:

  npm ci
  npm run vectors:start
  npm run ingest
  npm run index:vectors
  npm run dev

Open the local URL printed by the development server.

Validation and production build:

  npm test
  npx tsc --noEmit
  npm run build

Hosted deployment uses the Sites source synchronization, packaging, and private
publication workflow. A local build alone does not publish the application.

9. ACCEPTANCE AND TESTING REQUIREMENTS
- All 13 documents and 61 initial sections are indexed with unique chunk IDs.
- Leave questions retrieve the correct notice and entitlement qualifications.
- Purchase-approval questions retrieve the finance approval matrix.
- Remote-work paraphrases retrieve applicable workplace requirements.
- Lost-device questions retrieve security reporting requirements.
- Document scope excludes results from other documents.
- Empty or unrelated questions do not fabricate evidence.
- Missing API keys produce clearly labeled retrieval-only results.
- Invalid citations and provider failures do not produce a fabricated answer.
- Verify the page, status endpoint, input validation, and retrieval endpoint.
- Pass TypeScript checks and the production build.
- Complete browser visual/accessibility review and live-model evaluation before
  claiming full end-to-end verification.

Initial pre-vector verification: 12 automated tests, TypeScript, production build, and
local page/API checks passed. Provider tests use mocks. Visual browser testing
and live LLM answer quality were not verified at the initial handoff.

10. LIMITATIONS AND FUTURE ROLLOUT REQUIREMENTS
- Retrieval combines semantic embeddings and BM25 when configured.
- Cross-encoder reranking is not included; cosine thresholds need evaluation.
- Citation-number validation does not prove that each claim is supported.
- Questions are independent; follow-up questions must include their subject.
- History and bookmarks do not synchronize across browsers or devices.
- Access applies to the entire corpus, not individual roles or documents.
- Runtime uploads, PDF parsing, OCR, and enterprise document sync are not included.
- Before a broader rollout, evaluate real model answers on an approved question
  set and add application-level quotas, rate limits, and operational monitoring.
- Add document permissions, durable user storage, or additional reranking if
  the deployment's scale and access requirements call for them.
